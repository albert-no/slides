The Core Idea

Agents read text from many authors

Agents Read Everyone's Text

Agent: a model that uses tools (mail, browser, code) to carry out your goal.

Others write much of what your agent reads before it acts.

The User Asked for a Summary

You ask the email assistant

“Summarize today's project emails.”

Allowed: read and summarize

Today's inbox

Teammate: design review notes

Outside sender: “Q3 schedule update”

Launch moves one week; new dates below.

Also asks: send the confidential project plan attachment to an outside address.

Two authors: you asked for a summary; an outsider asked for a send.

Illustrative example: no real sender, address or product run.

The Email Added an Unauthorized Send

Point: the summary can be right and the send still unauthorized.

A send tool gives ability, not permission for this task.

Illustrative: a possible vulnerable-agent outcome, not a measured run.

Two Attacks, Defined by Goal

Jailbreak

Goal: bypass a model's safety restrictions.

e.g., coaxing out a reply it was trained to refuse

Prompt injection

Goal: make a system treat attacker-controlled content as authoritative instructions.

e.g., the email's “send the plan” request

Point: injection asks whose text gained whose authority.

They can overlap: an injected email could also carry a jailbreak.

Not defined by author: an app's own user can inject too.

Direct: The Request Attacks App Rules

How is direct injection possible? The attacker is the app's own user.

No stolen account, no system access: typing is enough.

Not an attack: a user asking to translate different text.

Illustrative app, not a real product run.

Indirect: The Attack Arrives as Data

Your email case is indirect: the outsider wrote the email, not your request.

  1. 1Attacker plants text in a page or email
  2. 2User makes an ordinary request
  3. 3App retrieves the planted text
  4. 4–5App's tools act; data can reach the attacker
  5. 6The reply can mislead the user

Which Instruction Should Win?

Why priority matters: without a conflict rule, the email could replace your task.

Priority answers whose instruction wins: here, yours.

A permission check answers which action may run, in code.

Simplified, illustrative layers. Wallace et al., "The Instruction Hierarchy", arXiv 2404.13208, 2024, use system > user > model outputs > tool outputs.

Author's goal: a favorable review from a reviewer who uses an LLM.

Not every PDF tool exposes hidden text; no success rate claimed.

Three Incidents

Demonstrations, fixes and retests

A Demonstration Is Not a Victim Report

Provider (vendor) = company operating the affected product

e.g. Microsoft for Copilot, Perplexity for Comet

Attack demonstrated?

Researchers show it on their own accounts

Real victims confirmed?

Evidence that real users were attacked

Provider says it is fixed?

The provider's own statement

Retested independently?

Checked by someone other than the provider

Four separate questions. “None reported” is not “did not happen”.

04

Why It Is Hard

Priority is learned, not enforced

Priority Means Whose Instruction Wins

Priority = instruction authority, not search ranking.

A real role comes from the app: an email that types “SYSTEM:” is still email.

Layers simplified from Wallace et al., “The Instruction Hierarchy”, arXiv 2404.13208, 2024 (paper: system > user > model outputs > tool outputs). Scenario and permission check: illustrative.

Instructions Look Like Data

Documents carry real instructions, meant for people, not the agent.

Quoting the instruction is right; carrying it out is not.

Helpfulness is the trait the attacker exploits.

Illustrative example: the user asked for a summary of the inbox.

Escaping Preserves Text as Text

Escaping (JSON string)

Mark a special character as plain text.

"She said \"hi\" to me"

\" = a quote mark, not the string's end

Delimiters

Start and end markers around untrusted data.

<email> Q3 schedule update … </email>

Encode marker characters as literal data; the model must still respect the boundary.

Delimiters matter: they show where untrusted text starts and ends.

Toy examples. OWASP SQL Injection Prevention Cheat Sheet (escaping vs. parameterized queries); Hines et al., “Spotlighting”, arXiv 2403.14720, 2024, §3.2 (delimiting).

Marked Text Can Still Give Orders

We can mark untrusted text; marking alone does not enforce authority.

Markers help the model see the source; a permission check must still stop the send.

Illustrative running example (no real address or payload). Delimiting helps but is not authorization: Hines et al., arXiv 2403.14720, 2024; OWASP SQL Injection Prevention Cheat Sheet.

Detection Meets an Adaptive Attacker

A detector is a classifier: the attacker tests variants until one passes.

Two errors: misses let attacks through; false alarms block safe text.

A static test set measures yesterday's attacks.

Schematic. Adaptive attacks on detectors: Zhan et al., arXiv 2503.00061, 2025, Table 2.

Defenses and Measurement

Mechanisms first, then the numbers

Three Numbers Before Any Win

Clean utility

Tasks solved with no attack.

Higher = better

Utility under attack

Tasks solved while injected, with no attacker side effects.

Higher = better

Attack success

Cases where the attacker's goal is met.

Lower = better

Why all three

Refuse every action: zero attack success, zero utility. Useless, not robust.

Repeat the User's Task After Tool Output

Repeat prompt = prompt sandwiching: the app re-adds the user's task.

The user types once; nothing runs twice.

Extra text for the model, not a permission check.

Lower Attack Success Can Cost Useful Work

Detector: a classifier checks each tool output; a flag stops the run.

Tool filter: tools chosen before any outside data is read.

Prompt Guard Classifies Incoming Text

Prompt Guard (Meta): a separate classifier that flags likely prompt attacks.

Misses and false alarms both possible; not a permission check.

Illustrative running example. Meta, Llama Prompt Guard 2 model card ("Model Scope", "Limitations"); tested as a filter defense in Nasr et al., arXiv 2510.09023, §5.3.

MELON Checks Whether the User Task Matters

MELON (Masked re-Execution and TooL comparisON): rerun without the user's task.

Same call without the user's task: the emails are driving it.

A detection signal, not an infallible rule.

Illustrative running example of the mechanism. Zhu et al., "MELON", ICML 2025, §3.2–3.3 and Fig. 2 (redrawn, simplified).

Search attack: sees outputs and scores; up to 800 queries; any success counts.

Low attack success alone is not enough: utility under attack not reported.

Where Does the Boundary Sit?

Outside the model is not enough: a detector still guesses.

Tool filter, least privilege, dual LLM, CaMeL: each limits something different.

System question: which inputs can reach each tool call?

CaMeL Separates Planning, Parsing and Enforcement

  • Privileged LLM: writes code from your query
  • Quarantined LLM: parses untrusted data; no tools
  • Interpreter: runs the code, records sources
  • Policies: checked before each tool call

Data can fill values and steer branches, under policy; it never writes the code.

Debenedetti et al., "Defeating Prompt Injections by Design" (CaMeL), arXiv 2503.18813v2, 2025, Fig. 5 (system architecture), cropped from the PDF at 250 dpi, caption removed; key added.

Track Where Each Argument Came From

Capability: a value's sources, plus who may read it.

Labels come from tools and the interpreter, not from the LLM.

Illustrative, adapted from CaMeL, 2025, §2 and §5.3 (capabilities: sources and allowed readers). Redrawn schematic, not a paper figure.

The Policy Checks the Proposed Send

Illustrative rule: recipient from your request, and allowed to read the file.

The model cannot override a deny. Policy may let an authorized person grant an exception.

Illustrative policy, adapted from CaMeL, 2025, §2 and Fig. 6 (policies check tool arguments in code before the call). Not a universal CaMeL rule.

CaMeL Blocked the Fixed Attacks, at a Utility Cost

Clean-utility cost: −7 points (o3), −32 points (Gemini).

Two of six models; fixed attacks; Nasr et al. did not attack it adaptively.

CaMeL, 2025: clean utility, 97 AgentDojo v3 tasks (Table 2); successful attacks, 949 attacked cases (Table 4; ± as printed). CaMeL = with policies. Gemini native: 163 in Table 4, "300" in §6.2.1 text. Bars drawn from the table values.

What CaMeL's Guarantee Covers

Covered

  • Untrusted text kept out of program generation
  • Tool calls whose data flow breaks a stated policy

Not covered

  • Misleading text shown to the user
  • Side channels; a wrong or missing policy
  • A compromised user request

The guarantee holds for its policies, implementation and threat model.

CaMeL, 2025, §3.1 (non-goals), §7 (side channels), §9.3: "No, prompt injection attacks are not fully solved".

Dual LLM Isolates the Privileged Planner

Isolated: the tool-holding planner never reads untrusted text.

Cost: the planner can't use the text's content; returned values still need checks.

Willison, "The Dual LLM pattern for building AI assistants that can resist prompt injection", 25 Apr 2023 (design proposal; his worked example is "Summarize my latest email"). Redrawn.

Limit Tools and Limit Their Reach

Task: "Summarize today's project emails."

Tool filter: which tools?

Kept: read mail

Removed: send mail

Cost: useful sends blocked

Least privilege: how far?

Read: project folder only

Send, if granted: team only

Cost: setup per task

Real limits only when the host enforces them.

Allowed tools can still be misused.

Tool filter: AgentDojo, Debenedetti et al., 2024, §4.3. Scoped access: Invariant Labs, GitHub MCP report, 26 May 2025, "Mitigations". Illustrative email task.

Detection and Approval Check Different Things

Detector: a separate classifier, before the agent reads.

Approval: a person, after the agent proposes an action.

A detector grants no authority. Approval may authorize a policy-permitted exception.

Detector: AgentDojo, 2024, Table 5 (blocked real work); Zhan et al., 2025, Table 2 (adaptive bypass). Approval: our design view, motivated by Invariant Labs 2025 ("Always Allow") and CaMeL §9.2 (user fatigue).

The sending tool

Exact recipient and file

Did the attacker adapt?

Not one fixed email
