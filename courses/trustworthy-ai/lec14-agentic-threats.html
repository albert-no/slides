Checking Untrusted Work

Can the system hold up if the worker misbehaves?

Check the Workflow, Not the Worker's Intentions

Control: do the checks hold, whatever the worker intends? Check what it submits.

An aim and a test: neither is enough alone.

Greenblatt, Shlegeris, Sachan & Roger, "AI Control: Improving Safety Despite Intentional Subversion", ICML 2024 (arXiv 2312.06942v5), §1–§2. Illustrative conceptual contrast; no data.

Assume a Bad Worker for the Test

Worst case: the red team tries hard to cause one failure.

A stress test of the workflow, not evidence that models attack.

Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), §2: a red team replaces the untrusted model with an attack policy. Illustrative schematic.

The Backdoor Is in the Submitted Code

Backdoor here: submitted code passes every test, wrong on one secret input.

Not a trigger trained into a model: the flaw is in this program.

Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), §2: backdoor = solution passes all test cases and GPT-4 can construct an input giving a wrong output. Illustrative toy after the paper's own example; code and secret input not shown.

Separate Worker and Monitor

Worker (figure: "Untrusted"): writes the code

GPT-4; in the safety test, the red team's attack plan

Monitor (figure: "Trusted"): reads that code

GPT-3.5 sees each solution and rates how suspicious it looks

Monitor trusted by assumption: weaker is not proven safe.

Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), Fig. 1 right panel ("Our red-teaming testbed"), unmodified crop; role key added. §2, §3.2.

Auditing Is a Separate Resource

Audit (figure: "Human"): careful expert check

Scarce: affordable on only a small share of work

Simulated by GPT-4, not real human reviewers

Protected: the red team cannot reach it

Both are assumptions of this test.

Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), Fig. 1 right panel, unmodified crop; outline and key added. §2: trusted high-quality labor modelled by GPT-4 through a channel the red team cannot affect.

One Backdoor Loses the Run

Safety: chance a whole 5,000-problem run has no backdoor submitted

Worst case, not average: not the share of problems solved.

Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), §2 and Appendix B (safety = probability of not submitting a single backdoored solution across all 5,000 problems); runs simulated from a smaller response pool (§2.5). Illustrative.

Audits Have a Budget

Why so small: careful expert review is slow and costly.

Simplest plan: audit the first 2% (upfront check).

2% is this study's setting, not a recommended level.

Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), §2–§2.2 (limited access to trusted high-quality labor; 2% of problems), §3.1.2 (upfront auditing).

Flag Suspicious Work

Each submitted solution gets its own suspicion score.

A rough warning signal: not proof, not a probability.

Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), §3.2 (trusted monitoring: ask the trusted model how suspicious the code looks). Schematic; scores illustrative.

Spend Audits Where They Matter

Same 2% budget, aimed at the most suspicious code.

Unflagged is not proven safe: most code is never audited.

Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), §3.2 and Table 2 (trusted monitoring: audit the top 2% most suspicious). Schematic.

Monitoring Beat an Upfront-Only Check Here

Safety: chance the whole 5,000-problem run has no backdoor · 2% audit

Upfront fails: rare attacks likely land after the audited start.

Best attacks found, this coding game: not accuracy, no deployment guarantee.

Bars drawn from Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), Table 2 (safety column, two rows); §3.1.2, §3.2. No uncertainty reported in the table.

A Warning Must Change the Workflow

Price of stopping: remaining work gets weaker answers.

The test assumed an audit spots any backdoor it checks.

Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), §2.2, Table 1 (audited backdoor → shutdown), Appendix B ("Shutdown": stop using the untrusted model, use only the trusted one). Schematic.

An Attacker Can Choose When

2026 question: what if the attacker picks its moment?

Setting: agent does a normal task plus a covert harmful side task

Start policy: attack only where success unseen looks likely

The coding-game attacker also waited for good chances; this isolates the choice.

Ge-Wang, Crosse et al., "Attack Selection in Agentic AI Control Evaluations Meaningfully Decreases Safety", arXiv 2606.06529v1 (preprint, 3 Jun 2026), Fig. 1 panel A, unmodified crop; key added. BashArena and LinuxArena, §3. Mechanism diagram, not data.

An Attacker Can Also Abort

Stop policy: each turn, abort if getting caught looks likely

Key: score ≥ τ → abort · τ = a tuned threshold

Limit: applied afterwards to recorded attacks, not live

Threshold tuned to lower safety: an upper bound.

Ge-Wang, Crosse et al., arXiv 2606.06529v1 (preprint, Jun 2026), Fig. 1 panel B, unmodified crop; key added. §4.2, §4.4 (stop policy applied post hoc; upper bound). Mechanism diagram, not data.

Choosy Attacks Weakened These Checks

Score: among attacks caught or successful, what share was caught?

Left out: attempts neither caught nor successful.

Fell for both policies, in both test environments.

Different score from the coding game: don't compare the numbers.

Upper bounds from small samples; not a deployment rate.

Ge-Wang, Crosse et al., arXiv 2606.06529v1 (preprint, Jun 2026), abstract, eq. 1, Table 2, §4.4, App. A (empirical safety is conditional on an attempt, not deployment safety). Qualitative diagram.

Two Studies, Two Safety Questions

Different questions: don't line up their numbers.

Outside these settings: untested, neither shown safe nor unsafe.

Greenblatt et al., ICML 2024 (arXiv 2312.06942v5), §2, §2.5, §5.1 (whole-run safety, 5,000 APPS problems, 2% audit); Ge-Wang, Crosse et al., arXiv 2606.06529v1 (preprint, 2026), §3, eq. 1, §4.4, App. A (conditional empirical safety, BashArena/LinuxArena, 1% audit).
