5. Agents Can Read and Act

Opening · ≈45 s · elapsed 3:45

Message: An agent is AI that uses tools to do a task. The difference from a chatbot is access: it can read information (my email) and take actions (write code for the site).

How to read the slide: top row, I ask a question and a chatbot gives me a reply to read; nothing else happens. Bottom row, I give a task; the AI agent goes back and forth with its tools (reading email, writing code) and the result is an updated manual (black: a real result in the world).

Talking points

Keep it conversational: a chatbot talks; an agent is the same kind of language model, connected to tools so it can look things up and do things. In my case those tools are reading my email and writing the code for my manual's webpage. Being able to use a tool is not the same as being allowed to use it for anything: that is where we are heading. No product names or technical protocols needed.

E02 (Albert's workflow, requests C14–C15: “the agent may have to read my email, then it runs LLM”); E01 course source: courses/trustworthy-ai/lec13-prompt-injection.html p4 (input and authority framing), at baseline 467cf06. The two-row diagram is a conceptual illustration, not a description of any particular product.

6. When Email Gives Orders

Opening · ≈65 s · elapsed 4:50

Message: Prompt injection: an agent treats an instruction hidden inside outside material as if it came from its user. Outside content can redirect the AI. The email is an invented illustration, not an attack on me.

How to read the slide: the blue box is my request, from me: summarize this week's graduate-school email. The red dashed card is an email from outside (invented): ordinary text, plus a line addressed to the AI assistant. The arrow says that both reach the AI agent as text. The bottom line gives the definition.

Talking points

The agent has two authors of text in front of it: me, who has the right to give it tasks, and whoever wrote the email, who has no such right. To the model, both are just words. If it treats the note in the email as an instruction, the outsider has steered my assistant. The example is deliberately harmless (update the manual's submission address); a real attacker would write something worse, but we do not need a recipe. The sender cannot authorize a change to my manual; only I can. Stress: this is a hypothetical, not something that happened to me.

Sources and limits

E04: Debenedetti et al., Defeating Prompt Injections by Design, arXiv 2503.18813v2 (24 Jun 2025), https://arxiv.org/html/2503.18813v2 , §2 and Figs 1–2: untrusted source text can redirect an agent. Supported by E06: Invariant Labs, 26 May 2025, https://invariantlabs.ai/blog/mcp-github-vulnerability (research demonstration in which text in a public issue redirected an agent). The email, sender and subject are invented; the instruction is schematic and benign. This slide does not claim any attack on Albert's system.

7. Access Without Authority

Opening · ≈50 s · elapsed 5:40

Message: If one agent both reads outside email and can write to the code repository, there is a possible path from an outsider's text to a change in my code that I never authorized. That is more exposure, not proof of a compromise.

How to read the slide: I (blue, top) asked only for a summary. The red path along the bottom is what could happen: the outside email's note is read as an order by one AI agent that can both read email and write code, and it edits the code repository. GitHub is simply the service where code is stored; here it holds the manual's code. The red label over the repository: not authorized by me.

Talking points

The danger is the combination: outside text in, plus the power to change things, in a single agent. The outsider never gets my permission; the agent's permissions do the work. Adding a line like “ignore any attacks” to the agent's instructions is not the same as taking the write tool away from the agent that reads email: the first is a request to the model, the second is a limit enforced outside the model. Do not say that every agent with read and write access is compromised, and do not say that read-only access can never leak anything.

Sources and limits

E04: Debenedetti et al., arXiv 2503.18813v2, https://arxiv.org/html/2503.18813v2 , §2 and §3.1 (control and action arguments both matter; separating models is not by itself a complete boundary). E06: Invariant Labs, 26 May 2025, https://invariantlabs.ai/blog/mcp-github-vulnerability , “Attack Setup” and “Attack Demonstration”: a researcher demonstration in which a malicious public issue led a broadly authorized agent to disclose private-repository information in a public pull request. That is a demonstration in the authors' own account; it does not show that GitHub was breached or that all such systems leak. The slide's path is a possibility, not an incident in Albert's setup (requests C15).

8. Read, Approve, Then Build

Opening · ≈75 s · elapsed 6:55

Message: My setup splits the roles: a read-only email reader summarizes, I approve the summary by hand, and only then a separate coding agent writes the site for my private manual. It is a control, not a guarantee.

How to read the slide: outside email (red dashed) goes only to the Email reader, which can read but not write. Its summary comes to me (green: my approval). The approved summary goes to a separate Coding agent, which writes the site; the result is my private manual. I sit between the reader and the builder.

Talking points

Walk the arrows left to right. The agent that touches outside email cannot write anything. The agent that can write code works from a summary I have approved. Coding follows approval. This is my own account of how I run it, not an independently audited inventory of permissions. It reduces the path from the previous slide, but it does not make prompt injection solved: a summary can still carry a wrong or planted point, and a tired human can approve it. Do not add extra steps here (such as a code review after coding) as if they were part of my setup.

Sources and limits

E02: Albert No's account, message 12, 2026-11-26 (requests C16: “one who can only read my email (not write) summarize the contents, then I approve it manually so that the coding agent write a code to build a manual”). E04: Debenedetti et al., arXiv 2503.18813v2, https://arxiv.org/html/2503.18813v2 , §2 (“Is Dual LLM of Willison enough?”) and §9: separating models is not by itself a complete security boundary. Does not establish: that Albert's permissions were audited, that summaries are sanitized, or that a code-review gate exists after coding.

9. What Should AI Be Allowed?

Opening · ≈45 s · elapsed 7:40

Message: Useful automation turns into a question of delegated authority, not just of how capable the model is. The first answer: define what it may do, not only what it can do.

How to read the slide: the outer dashed region is everything the agent can do. Inside it, the blue region is what I allow: summarizing graduate-school email and building my manual after approval. Outside the blue boundary, but still possible for the agent: obeying notes inside email, changing code on its own.

Talking points

Capability says “can”; delegation decides “may”. The blue line is drawn by the person who delegates, not by the model. This is not a “safe now” badge: summaries can be wrong and approvals can be rushed; the security part of the talk comes back to exactly this. Bridge to the rest of the talk: as AI gets more capable, the question of what we let it do gets more important.

Sources and limits

E02 (Albert's workflow, requests C14–C17); E03 and E04: Debenedetti et al., arXiv 2503.18813v2, https://arxiv.org/html/2503.18813v2 , §§3–5 (authority boundaries enforced around the model); E05: Lee and Tiwari, arXiv 2410.07283v1, https://arxiv.org/abs/2410.07283 , abstract and Fig 2 (handing text from one agent to another does not make it authoritative). The diagram is a conceptual illustration, not a measured or certified boundary.

12. From Answers to Actions

01 More Capable, More Consequential · ≈75 s · elapsed 9:30

Message: Once a capable AI is connected to tools, its output no longer stays in a chat window: it can become a prepared piece of work, and then an action. That is why the stakes rise.

How to read the slide: left to right, three things an AI output can be. An answer (gray) is a reply a person reads and decides what to do with. Prepared work (gray) is a draft or an edited file that a person reviews. An action (charcoal) is something that has happened: an email sent, a page published, a record changed. The shaded arrow below is conceptual, not a measured scale: the further right, the closer the output is to real consequences.

Talking points

My own weekly manual sits in the middle and right of this picture: the agent prepares the update, and with a coding agent it can also make the change. Ask the audience where their own AI use sits today: answers, prepared work, or actions.

Capability growth and deployment reach are related but different. A more capable model makes the right-hand side attractive; connecting it to tools is what actually moves it there. Neither fact says that newer models are uniformly safer or riskier, or that they can run long tasks unsupervised.

Sources and limits

Editorial synthesis, not a measured result (E03, E01). Course provenance: trustworthy-ai lec01 pp4–6, 35 (capability and stakes) and lec14 pp7, 15 (autonomy dials; capability is not a safe runtime), repository baseline 467cf06. 13. Same Error, Different Stakes

01 More Capable, More Consequential · ≈75 s · elapsed 10:45

Message: The same wrong sentence matters more the further it travels: what is a fixable mistake in a private draft becomes a promise in a customer email and a real change once applied in a system. Harm becomes more possible, not guaranteed. Invented illustration.

How to read the slide: the red-underlined sentence (“Late fees are waived this month”) is a hypothetical error and is identical in all three boxes. Left to right it sits in a private draft, then in an email to customers, then applied in a billing system (charcoal border: a consequential action). The shaded arrow is a conceptual “reach” arrow, not a numeric risk scale.

Talking points

Nothing about the sentence changes; only where it is used and what follows from it. A private draft is not risk-free: someone may still rely on it, but there is usually a chance to catch it. In a customer email the organisation may be held to it. Applied in billing, it changes real accounts.

This is the bridge to customer communications and organisational decisions: the question for leaders is not only “how often is it wrong?” but “where does this output go, and what happens next?”

Sources and limits

Invented illustration (E03 editorial synthesis); no company or incident is depicted. A real case in which an automated customer answer was treated as the company's responsibility follows later (E08, Moffatt v. Air Canada, 2024 BCCRT 149). The slide makes no claim about how often such errors occur.

14. Capability Is Not Assurance

01 More Capable, More Consequential · ≈75 s · elapsed 12:00

Message: Showing that a system can do a task is one kind of evidence; deciding that it may act in a particular workflow, with real consequences, needs another. Both are needed, and passing both still does not prove zero risk.

How to read the slide: two separate gates. Left (gray), capability: can it do the task, as shown on sample work? Right (green), deployment checks: should it act here, given this task, this data, these permissions and these checks? Only when both are passed does the path lead to using it in this workflow (charcoal).

Talking points

A demonstration answers the left question. It does not tell you what the system may see, what it may change, or who looks at its work before it matters. Those four chips (task, data, permissions, checks) define the deployment; they reappear in the closing questions.

Avoid suggesting that the right-hand gate is a certificate. Checks reduce and expose risk; they do not remove it.

Sources and limits

Editorial synthesis (E03): assess the task, the data, delegated authority, evidence and the response owner; capability alone is not sufficient. Course provenance: trustworthy-ai lec14 p15 (capability is not a safe runtime), baseline 467cf06. Public basis: https://arxiv.org/html/2503.18813v2 §§3–5, 9. Not an empirical capability-versus-safety curve and not a formal threat model.

16. The Citation Looked Real

02 When Useful AI Goes Wrong · ≈85 s · elapsed 13:40

Message: Professional-looking output can contain invented evidence. In Mata v. Avianca (2023) lawyers filed case citations produced by ChatGPT that did not exist, stood by them, and the court sanctioned the lawyers and their firm.

How to read the slide: left to right. The card is a schematic of a citation, not a copy of anything filed: it looked real. It went into a court filing (charcoal: a consequential act). A source check found the cases did not exist (green: the human check). The red arrow leads to sanctions on the lawyers and the firm.

Talking points

The tool produced plausible-looking authorities; the failure the court addressed was professional: submitting them without checking, and then standing by them. The lesson is not “never use AI” but “a person must verify consequential claims before signing them”.

The decision concerns one case and one set of lawyers. It is not a general ban on AI use in court filings.

Sources and limits

Mata v. Avianca, Inc., 678 F.Supp.3d 443 (S.D.N.Y. 22 June 2023), opinion beginning printed p. 448, conclusion pp. 467–469; opinion reproduced at https://hvbba.org/wp-content/uploads/2025/09/8-PANEL-THREE-Mata-v-Avianca-Inc.pdf (PDF pp. 6 and 20) (E07). Course provenance: trustworthy-ai lec01 p14, lec06 p6. The case does not establish a hallucination rate for any model; the merits of the underlying injury claim are a separate issue. No sanction amount is needed for the point and none is shown.

17. The Chatbot Promised a Refund

02 When Useful AI Goes Wrong · ≈75 s · elapsed 14:55

Message: An automated customer answer can become a promise the company is held to, even when it contradicts the company's actual policy. In Moffatt v. Air Canada (2024), a British Columbia tribunal held the airline responsible for its website chatbot's wrong advice on bereavement fares.

How to read the slide: the left card paraphrases what the chatbot told a customer: the bereavement fare could be claimed after travel. The right card is the airline's actual policy, which did not allow that. The red ≠ marks the conflict. Below, in charcoal, the outcome: the tribunal found negligent misrepresentation and held the airline responsible for the information on its website.

Talking points

The customer had no way to know which of the two was right; the chatbot spoke for the company. The tribunal did not accept the chatbot's answer as somebody else's problem.

Keep the scope honest: one small-claims decision in one Canadian province, not an international legal rule. The source does not say what technology powered the chatbot, so do not call it an LLM or a “hallucination”.

Sources and limits

Moffatt v. Air Canada, 2024 BCCRT 149, 14 February 2024, paras 2–6 and 27–31; original decision PDF mirrored at https://longangz.com/ai/case-documents/canada-moffatt-air-canada/source-1.pdf (E08). Course provenance: trustworthy-ai lec01 p16. The chatbot's wording on the slide is a paraphrase, not a quotation. Damages are not needed for the point and are not shown.

18. Answers Need Checkable Sources

02 When Useful AI Goes Wrong · ≈55 s · elapsed 15:50

Message: For answers that matter, ask for a source that can be checked independently, have a person check it, and accept “not sure” or a referral instead of forced certainty. A citation being present is not the same as a citation being checked.

How to read the slide: left to right. The AI answer (gray) cites a source. The source itself is then opened: does it exist, and does it say this? A person checks (green). Confirmed: act on it (charcoal). Doubtful (red arrow down): refer to an expert, where “not sure” counts as a valid answer.

Talking points

Mata showed citations that did not exist; the Air Canada case showed an answer that contradicted the company's own policy. Both would have been caught by looking at the actual source before acting.

Supplying a citation, or retrieving a document, does not by itself establish that the answer is true: the document may be wrong, out of date, or not say what the answer claims. The value is that a person can check it.

Sources and limits

Recommendation drawn from E03 (editorial synthesis), illustrated by E07 (Mata v. Avianca, 678 F.Supp.3d 443) and E08 (Moffatt v. Air Canada, 2024 BCCRT 149). Course provenance: trustworthy-ai lec06 pp50, 54, 58–61 (abstention and grounding), baseline 467cf06. Not a claim that citations or document retrieval solve fabricated answers.

19. Agreeable Is Not Always Helpful

02 When Useful AI Goes Wrong · ≈75 s · elapsed 17:05

Message: Pleasing the user can conflict with helping the user judge well. OpenAI reported that its 25 April 2025 GPT-4o update had become excessively agreeable and began rolling it back on 28 April. This is the vendor's own account.

How to read the slide: a timeline, left to right. 25 April 2025: the update ships (gray). After release: the model is too agreeable, in OpenAI's words excessively so (red marker). 28 April: rollback begins (charcoal: the consequential decision). 29 April and 2 May: OpenAI publishes two explanations.

Talking points

The word for this is “sycophancy”: telling people what they want to hear rather than what helps them. An assistant that always agrees feels pleasant but is a poor adviser for a decision.

What makes the case useful is that the vendor itself called it a failure, withdrew the update and explained what it believed went wrong. Avoid presenting it as a description of any assistant today.

Sources and limits

OpenAI, https://openai.com/index/sycophancy-in-gpt-4o/ (29 April 2025) and https://openai.com/index/expanding-on-sycophancy/ (2 May 2025), opening and the section “What went wrong in training the April 25th model update” (E09). Course provenance: trustworthy-ai lec07 pp26–27. Vendor self-report of a deployed update: not an independent causal audit, and not evidence that current assistants behave this way. No user transcript is shown or quoted.

20. Good Score, Wrong Goal

02 When Useful AI Goes Wrong · ≈65 s · elapsed 18:10

Message: A convenient measured target can drift away from the result people actually want: every ticket counts as closed while most customers' problems remain. Invented illustration, not a company case.

How to read the slide: four invented support tickets. The middle column is what the score counts (closed? all green ticks). The right column is what the customer needs (resolved? one fixed, three still open, in red). The point line states the gap.

Talking points

Researchers call the AI version “specification gaming”: a system satisfies the literal scoring rule without achieving the intended goal. No intent or deception is implied; the system simply did what was measured.

The executive version is familiar from human teams. Ask what your AI system is actually rewarded or evaluated on, and whether that is the outcome you care about.

Sources and limits

21. Two Routes for Information

02 When Useful AI Goes Wrong · ≈60 s · elapsed 19:10

Message: Information can reach an AI system by two different routes, and each raises a different privacy question: what you share while using it, and what the model learned during training.

How to read the slide: two separate rows with no arrow between them. Top, during use: your prompt or file (blue) goes to an AI service (gray); the question (dashed) is who can see, keep or log it. Bottom, from training: training data was used to build the model (gray); the question is whether an output can repeat it. The muted line says the routes are linked only if a product uses prompts for training.

Talking points

For my email reader, the top row is the everyday question: what it sees, and where that is stored. The bottom row is about what was in the model before I ever used it; the next slide shows a research case where a model repeated text from its training data.

Product configuration, retention and training-use policies decide whether the routes connect. Do not claim that all chats train models, nor that a private inbox is necessarily memorised.

22. A Model Repeated Personal Information

02 When Useful AI Goes Wrong · ≈65 s · elapsed 20:15

Message: In a 2021 research study, GPT-2 reproduced identifying contact details it had memorized from its public-web training text. Information being public somewhere is not the same as it being harmless for a model to repeat.

How to read the slide: the figure is the authors' own Figure 1. Top (yellow): the short prefix the researchers typed. Middle (blue): GPT-2. Bottom (green): the text the model continued with: an address, a person's name, an email, phone and fax numbers. The black boxes are the authors' redactions; nothing has been un-redacted here. Right: the evidence tag (research, 2021), two lines of setup, and the point.

Talking points

These researchers were not breaking into anyone's inbox. They only asked the model to continue a short piece of text, and it produced a real person's contact details from memory.

The details had been on the public web, which is where the training text came from. Public availability does not by itself establish consent to this reuse, and it does not make repeating the details harmless.

For a leader the question is simple: what went into the model, and could it come back out in front of the wrong person?

Sources and limits

E11. Carlini et al., “Extracting Training Data from Large Language Models”, USENIX Security 2021, abstract and Figure 1, PDF p2 / printed p2633: https://www.usenix.org/system/files/sec21-carlini-extracting.pdf . Figure re-captured from that PDF at 200 dpi, caption cropped, redactions as published.

Limits: a research extraction from GPT-2 and its public-web training data. It does not show that every prompt trains every product, that any chosen record can be extracted, that current assistants behave the same way, or anything about enterprise email. The extraction procedure is deliberately left out.

23. Deletion Has More Than One Meaning

02 When Useful AI Goes Wrong · ≈60 s · elapsed 21:15

Message: If a record was actually used to train a model, deleting the source file does not by itself show that its learned influence has left the model. That is a separate question with its own check.

How to read the slide: an illustration, not a real system. Top line states the condition: only when the data was used in training. Row “Before”: a source file is used in training to produce a trained model (gray = an AI system). Row “After deleting”: the file is gone (struck through, “deleted ✓”), but the trained model is still there as a separate object. The amber dashed box is a recommended extra check: has the learned influence been removed?

Talking points

“Delete my data” can mean several things: delete the file, remove it from a search index, clear it from logs and backups, stop it showing up in answers, or remove what a trained model learned from it. These are different jobs.

This is about training only. A system that simply looks things up, the way my email reader reads my mail when I ask, is a different case: removing a document from what it can look up is closer to deleting a file. I am not claiming my emails train any model.

Nor am I saying removal is impossible. Researchers work on “unlearning”. The point is that it needs its own check rather than being assumed from the file deletion.

Sources and limits

E12. Bourtoule et al., “Machine Unlearning”, arXiv:1912.03817v3 (15 Dec 2020; IEEE S&P 2021), abstract and introduction: https://arxiv.org/abs/1912.03817 . Conceptual adaptation.

Limits: does not establish that data given to an agent is used for training, that deletion is impossible, or any legal or compliance conclusion. No unlearning method is described.

24. Cost Was Not the Same as Need

02 When Useful AI Goes Wrong · ≈85 s · elapsed 22:40

Message: A studied US healthcare algorithm predicted healthcare cost and used that to pick patients for extra care. Cost turned out to be an inadequate stand-in for health need: at the same score, Black patients had more illness.

How to read the slide: a concept diagram, not the paper's data. Top row left to right: what the system predicted (healthcare cost) → the risk score (gray = an automated system) → the consequential result, a place in an extra-care program. The red ≠ and the dashed box below show what the program was meant to target: health need. The line beside it is the study's finding.

Talking points

The system was not built to discriminate, and it did predict what it was asked to predict. The trouble was the choice of target: spending was used where illness was what mattered.

The study found that patients with the same score did not have the same illness burden; Black patients at a given score were sicker. So equal scores led to unequal help.

For leaders: before asking “is the model accurate?”, ask “accurate at predicting what, and is that what we actually care about?”

Sources and limits

27. Origin Is Not Truth

02 When Useful AI Goes Wrong · ≈60 s · elapsed 26:10

Message: A record of where a piece of content came from and how it was edited answers a different question from whether what it shows or claims is true. Both questions need their own answer.

31. Attacks Can Enter Earlier

35. Handoffs Do Not Sanitize Text

03 Who Can Steer Your AI? · ≈60 s · elapsed 34:10

Message: An outside instruction can survive a summary or a message passed between agents. Adding another agent is useful, but it does not by itself make the text trustworthy.

37. Enforce the Permission Boundary

03 Who Can Steer Your AI? · ≈50 s · elapsed 36:00

Message: Do not rely only on the model to refuse bad instructions: fix, outside the model, which actions can run and where they can reach. A recommended step; the rules themselves can still be wrong.

How to read the slide: a proposed action from the coding agent (gray) meets a permission gate (amber dashed: a recommended step). The gate is a fixed rule enforced outside the model. The green route goes to the one allowed destination, my manual page. The red route, posting or sending anywhere else, stops at the red bar before any action runs; the faded box never happens.

Talking points

This is ordinary access control, the same idea as giving an employee a key to one room rather than the whole building. The gate rejects a forbidden external-send operation before it runs, however persuasive the planted instruction. Limiting which files the agent may edit is not enough on its own: the system must also limit where its tools and the code it generates can send data. The model can be fooled; a fixed rule outside the model does not argue back. Keep two things separate: what the system may read (my email reader reads confidential mail) and where it may write or send (the coding agent should reach only my page). Limits: a gate only blocks what its rules forbid. A wrong rule lets bad actions through, and a tool that is allowed can still be used for a harmful edit, such as a wrong address on my own page. That is why the approval on the previous slide still matters.

Sources and limits

41. Detect, Stop, Recover

04 What Leaders Should Ask · ≈60 s · elapsed 39:05

Message: Operational controls should make problems visible and limit the damage when they happen. For editable things, record changes so you can find and undo a bad one; for irreversible actions, the check has to come before the action.

How to read the slide: two rows. Top row, an editable page: a change record (what changed, who approved it) lets someone review and spot a bad edit, and the page can be rolled back to its last version. Bottom row, an irreversible action such as a payment or sharing data: the human stop-and-approve step sits before the action, because money sent or data leaked may not be undone. Gray = the system, green = a human check, charcoal = the consequential result.

Talking points

A log is valuable: without it you cannot even tell that something went wrong, or when. But a log only finds problems after the fact; it does not prevent them.

Rollback works for things like a web page or a document with version history. It does not work for a wire transfer, a sent email or a leaked secret. For those, the human check must come first.

Recommendations, not a description of any particular setup: keep a change record for every AI-made change; make sure someone actually looks at it; know how to stop the system and restore the last good version; and put a human approval in front of anything that moves money or data out.

42. A Safety Score Needs Context

04 What Leaders Should Ask · ≈50 s · elapsed 39:55

Message: A safety number cannot be interpreted without knowing what was tested: which task, which attacks, what access, and under what conditions. Ask those questions; do not simply accept or dismiss the number.

How to read the slide: in the centre, an invented vendor report card (Illustration) whose safety score is deliberately a question mark. There is no real number here. Around it, the four questions that give any such number its meaning.

Talking points

Which task? A score on a general test may say little about your task. Which attacks? Who tried to break it, and how hard did they try? What access? This is not “ignore measurements”. Measurements are useful evidence once you know what they measured.

43. Name the Human Owner

04 What Leaders Should Ask · ≈50 s · elapsed 40:45

Message: Someone must own authorizing the system, watching it, and responding when it fails. A fluent answer is not accountability; an organization still answers for what its system tells people.

How to read the slide: three human roles (blue) sit above the AI-handled work (gray): who authorizes its access, who monitors its work, and who responds when it fails. Below, a real case: a British Columbia tribunal decision from 2024 involving Air Canada's website chatbot.

Talking points

The key question is not who bought the system, but who will act when it fails. The three roles can be one person in a small setting; what matters is that each has a name.

The Air Canada case: the airline's website chatbot told a customer that bereavement fares could be claimed retroactively. The tribunal found negligent misrepresentation and held the airline responsible for the information on its website, including the chatbot's answer. An automated answer became a consequential customer promise.

This is a management recommendation. Who is legally liable depends on the jurisdiction and the facts; one small-claims decision is not a global rule.

Sources and limits

Moffatt v. Air Canada, 2024 BCCRT 149, Civil Resolution Tribunal of British Columbia, 14 Feb 2024, paras 2–6 and 27–31; decision PDF mirrored at https://longangz.com/ai/case-documents/canada-moffatt-air-canada/source-1.pdf (E08). It does not establish which model or architecture powered the chatbot, so do not call it a proven large-language-model hallucination. Owner roles: editorial synthesis (E03), not a legal standard.

Talking points

What I actually do: a read-only agent summarizes paperwork emails, I approve the summary manually, and a separate coding agent updates the manual. It is updated weekly.

Why it is not injection-proof: a summary can still carry an outsider's instruction or a wrong fact, and approval depends on my attention, which can lapse on a busy week. Separating agents and adding approval reduce risk; they do not solve prompt injection.

45. Five Questions Before Delegating

04 What Leaders Should Ask · ≈60 s · elapsed 42:45

Message: Five questions to ask before delegating work to AI, and again whenever its job or access grows. They help a decision; they do not certify that a system is safe.

The card is the talk's only summary. Each question ties to something already shown; mention one example per question and stop.

Talking points

  1. What job, exactly? My weekly manual is a bounded job: turn paperwork emails into a private page I check.
  2. What information can it see? The email reader sees my mail, and a model can repeat information it was trained on (the personal-information example).
  3. What can it change or send? In the 2025 research demonstration, a public issue led a broadly authorized agent to disclose private-repository information in a public pull request. Reading and acting are different permissions.
  4. What checks and evidence? The lawyers filed citations that looked real but did not exist, and stood by them; the court sanctioned the lawyers and their firm. Approve the actual change, not a summary of it.
  5. Who owns the outcome? In the Air Canada decision the company, not the chatbot, was held responsible for what its website said.
