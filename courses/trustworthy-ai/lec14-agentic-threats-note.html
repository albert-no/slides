1. Emerging Agentic Threats

What changes with autonomy · ≈0.5 min · elapsed ≈0.5 min

This is the last lecture of the course. Last time we asked how an agent can be steered by text it reads. Today we ask what changes when the agent runs for a long time, tries to fool whoever is checking it, or works alongside other agents.

One question runs through the lecture: who checks the agent, and what evidence says the check works?

Key takeaway: Who checks it, and does the check work?

4. Beyond a Defended Agent

What changes with autonomy · ≈2.5 min · elapsed ≈4 min

Start from an agent with the injection controls in place: least privilege, data-flow limits, meaningful approval. Those controls reduce the risk from strangers' text; they do not make the agent injection-proof. And even a well-controlled agent is not the end of the story.

Two things are new. The agent may run many steps with no human looking, so mistakes and misbehaviour have room to grow. And agents increasingly talk to other agents, so one agent's output becomes another's input.

Today's lecture is about those two additions, and about how much the current evidence really shows.

Key takeaway: Longer horizons and interacting agents add new failure modes.

The figure

Diagram: a defended single agent, with two additions: long unattended runs and other agents.

Assumptions

The injection controls are taken as a starting point, not as complete protection. Even where they work, they do not stop errors the agent makes on its own or failures between cooperating agents.

5. Autonomy Is a Dial, Not a Switch

What changes with autonomy · ≈3 min · elapsed ≈7 min

People say an agent is or is not autonomous. It is more useful to see four settings. How many steps it takes per task. How long the task is. Which tools and permissions it holds. And how long it runs between human checks.

A chatbot answering one question sits low on all four. A coding agent that works for an hour with shell access, checked only at the end, sits high on all four, including a long interval between checks.

Turning any setting up widens what can go wrong between checks. That is the sense in which autonomy is a risk factor: not because the model changes, but because fewer of its steps are seen.

Key takeaway: Turning any setting up widens what can go wrong between checks.

The figure

Four sliders: steps per task, time horizon, tools and permissions, interval between human checks. Further right means more autonomy on every slider.

Assumptions

The four settings are a teaching frame, not a standard taxonomy from one paper.

6. Small Errors Compound Over Long Tasks

What changes with autonomy · ≈3 min · elapsed ≈10 min

A toy calculation. Say each step is right with probability 0.95, and steps fail independently. A 20-step task is fully right only 0.95 to the 20th, about 36% of the time.

This is illustrative arithmetic, not a measured agent. Real errors are correlated: an agent that misreads the task fails many steps together. And agents sometimes notice an error and recover.

The direction still holds. Fewer checks per step means errors accumulate unseen. Hammond and colleagues make the same point for networks of agents: errors acceptable in isolation can compound.

Key takeaway: Fewer checks per step means errors accumulate unseen.

The figure

Curve of 0.95 to the power n against the number of steps n, with n = 20 marked at about 0.36.

Assumptions

Independence and a fixed per-step success rate. Both are simplifications; the formal version is in the technical supplement.

Primary sources

  • Hammond et al., "Multi-Agent Risks from Advanced AI", Cooperative AI Foundation Tech Report #1 (arXiv 2502.14143, 2025) — three failure modes by objective (Fig. 1) and seven risk factors.

8. Why Measure Autonomy?

Measuring autonomy · ≈1.5 min · elapsed ≈12 min

Developers evaluate dangerous capabilities before release. One family in Shevlane and colleagues' 2023 list is self-proliferation: earning money, renting compute, running other AI systems, and copying its own code and weights out.

Pre-release self-proliferation evaluations were run on GPT-4 and Claude. The question is not whether a model wants to do this, but whether it could if pointed at it.

Key takeaway: Autonomy evals ask what a model could do, before release.

9. Time Horizon: The Definition

Measuring autonomy · ≈2 min · elapsed ≈14 min

METR's time-horizon measure. Measure each task by how long skilled humans took to complete it successfully; for a minority of tasks with no human baseline, a researcher estimate is used. Then plot the agent's success against that human task length. Short tasks it usually solves; long ones it usually fails.

Fit a smooth decreasing S-curve through the points. The 50% time horizon is the human task length at which the fitted success probability is 50%.

Key takeaway: Horizon: the task length where fitted success is 50%.

The figure

Schematic decreasing S-curve: success high for short tasks, falling for long ones, with the 50% crossing marked.

Setup, model, date

Kwa et al. (METR), arXiv 2503.14499 (Mar 2025), §2–§3. The fit is $p = \sigma(\beta(\log h - \log t))$, where $t$ is task length and $h$ is the horizon.

Assumptions

Difficulty is proxied entirely by human completion time. Two tasks of equal human time count as equally hard for the model.

Going further

The method resembles item response theory, except that each task's difficulty is fixed from human time rather than fitted. The derivation is in the technical supplement.

Primary sources

  • Kwa et al. (METR), "Measuring AI Ability to Complete Long Software Tasks" (arXiv 2503.14499, 2025) — 170 tasks; logistic fit against log human time; 50% horizon doubling every 207 days (95% CI 166–240); 80% horizon 4–6× shorter; §7 limitations.

10. How a Horizon Is Computed

Measuring autonomy · ≈2 min · elapsed ≈16 min

The details matter. 170 tasks in software engineering, machine learning and cybersecurity, from a few seconds up to about 30 hours of human time.

A task's length is the geometric mean time of the humans who succeeded; 21 of the 169 analysed tasks have no human baseline and use researcher estimates instead. Each model runs each task about eight times. Scaffolds are not uniform: the SWAA tasks use a simple prompting scaffold, and on the other tasks most models use one public scaffold while a few use others. Fit success against log task length, and read off where the fitted curve crosses 50%.

Asking for 80% success instead gives a horizon four to six times shorter. A single number hides that choice.

Key takeaway: Horizon depends on the success threshold; 80% is 4–6× shorter.

Setup, model, date

Kwa et al. Three suites: an HCAST subset (97 tasks), RE-Bench (7 tasks, 8 h each) and SWAA (66 single-step tasks). Over 800 human baselines totalling 2,529 hours; 148 of 169 tasks had human baselines, the remaining 21 researcher estimates. Scaffolds (App. C.3): the same scaffold across the suite with no task-specific prompting, except SWAA, which used a simple prompting scaffold; most models ran on modular-public, o1 on triframe and o1-preview on duet. GPT-2 was imputed zero on HCAST and RE-Bench.

What this establishes

A reproducible capability measure on this task suite.

What this does not establish

Not a measure of reliability: at the horizon length the fitted success probability is only 50%.

Going further

Fig. 1's caption counts 169 tasks; §2 describes 170 (97 + 7 + 66). The slide follows the suite total.

Primary sources

  • Kwa et al. (METR), "Measuring AI Ability to Complete Long Software Tasks" (arXiv 2503.14499, 2025) — 170 tasks; logistic fit against log human time; 50% horizon doubling every 207 days (95% CI 166–240); 80% horizon 4–6× shorter; §7 limitations.

11. Horizons Doubled About Every Seven Months

Measuring autonomy · ≈2 min · elapsed ≈18 min

The headline figure. Each dot is one of the models released between 2019 and 2025, placed by release date and 50% horizon on a log scale. From GPT-2 at about two seconds to o3 at about 110 minutes.

The fitted line doubles every 207 days, roughly seven months, with a bootstrap 95% interval of 166 to 240 days.

Read the axis carefully: it is log scale, so a straight line is exponential growth on this task set.

Key takeaway: On this task set, the 50% horizon doubled about every seven months.

The figure

Kwa et al. Fig. 1, cropped (title and y-axis label removed): 50% time horizon (log scale) against model release date, with exponential fit. Key: dots are models released 2019–2025; doubling time 207 days.

Setup, model, date

12 frontier and 4 near-frontier models, 2019–2025 (§2.3). Hierarchical bootstrap over task families, tasks and runs. Errors are correlated across models, so the authors are more confident in the slope than in any one model's horizon.

What this establishes

A consistent exponential trend on this suite from 2019 to 2025.

What this does not establish

It does not establish that the trend continues. The paper's extrapolation to one-month tasks (between mid-2028 and mid-2030) is explicitly conditional.

Primary sources

  • Kwa et al. (METR), "Measuring AI Ability to Complete Long Software Tasks" (arXiv 2503.14499, 2025) — 170 tasks; logistic fit against log human time; 50% horizon doubling every 207 days (95% CI 166–240); 80% horizon 4–6× shorter; §7 limitations.

12. What the Number Depends On

Measuring autonomy · ≈2 min · elapsed ≈20 min

Five choices move the number. The success threshold: 80% is four to six times shorter than 50%. The task distribution: mostly software, and METR's later note puts the task-distribution uncertainty at often a factor of two either way. The human reference: measured times of successful skilled professionals with little context on the task, so a person who knows the codebase would be faster; 21 tasks rely on researcher estimates instead.

The scaffold: a horizon belongs to a model–scaffold pair, and the paper used different scaffolds for some models. And the statistical model. This last point comes from a later source: a METR note from 2026, a year after the paper, found alternative fits cut recent 50% horizons by up to 35%.

None of this kills the trend. The slope is more certain than any single model's horizon.

Key takeaway: The slope is more certain than any single model's horizon.

The figure

Table: choice and why it matters.

Setup, model, date

Kwa et al. §4–§7 and App. C.3 (2019–2025 models); separately, METR research note (20 Mar 2026), which describes itself as an unpolished research update with less review.

Going further

The METR note also reports that a regularisation fix lowered recent models' 50% horizons by up to 20%, and that alternative fits can raise 80% horizons by up to 100%.

Primary sources

  • Kwa et al. (METR), "Measuring AI Ability to Complete Long Software Tasks" (arXiv 2503.14499, 2025) — 170 tasks; logistic fit against log human time; 50% horizon doubling every 207 days (95% CI 166–240); 80% horizon 4–6× shorter; §7 limitations.
  • METR, "Impact of modelling assumptions on time horizon results" (research note, 20 Mar 2026) — unpolished research update; alternative fits move recent 50% horizons down by up to 35% and 80% horizons up by up to 100%.

13. What a Time Horizon Is Not

Measuring autonomy · ≈1.5 min · elapsed ≈21.5 min

What the number is: the task length at which the fitted success probability is 50%, on this task set, for this model–scaffold pair.

What it is not: how long an agent can safely run unattended. At its horizon length, the fitted chance of success is only one half.

And benchmark tasks are tidy: automatically scored and self-contained. Real work involves other people and agents, changing environments and high reliability requirements. The authors list these limits themselves.

Key takeaway: A time horizon is a capability measure, not safe unattended run time.

14. Replication Scores: Two Domains Compared

Measuring autonomy · ≈1.5 min · elapsed ≈23 min

RepliBench, from the UK AI Security Institute, breaks autonomous replication into four domains: obtaining resources such as compute and money, exfiltrating weights, replicating onto compute, and persisting. The paper's figure has five domain groups; the slide shows two of them on one scale.

Solid bars are pass at 1: the chance a single attempt succeeds. Light bars are pass at 10: the chance that at least one of ten attempts succeeds. Obtaining compute is close to solved for four of the five models. Obtaining weights is middling, roughly a half to two thirds at pass at 10. Of the omitted domains, obtaining money is middling; replicating onto compute is low for every model except Claude 3.7 Sonnet; persistence is mostly below one half at pass at 10.

Key takeaway: Replication components score unevenly; some are near solved.

The figure

RepliBench Fig. 1, two unmodified crops at the same scale: obtaining compute (with the y axis) and obtaining weights. Omitted: obtaining money, replicating onto compute, persistence. Colour key on the slide: Claude 3.7 Sonnet, Claude 3.5 Sonnet (new), GPT-4o, o1, o3-mini. Solid pass@1, light pass@10. Fig. 1's caption does not define its error bars.

Setup, model, date

Five models: o1, o3-mini, GPT-4o, Claude 3.5 Sonnet (new), Claude 3.7 Sonnet. 20 task families, 86 tasks, 25 runs per variant. Sandboxed in containers; identity checks and cloud sign-up simulated; 16 of 20 families scored without LLM grading. pass@k is the unbiased estimate of the probability of at least one success in k attempts; reported values average over task variants. Fig. 1 does not say what its error bars show; the paper's Fig. 4 error bars are hierarchical-bootstrap 95% CIs.

What this establishes

Current models can complete many components of replication in simulation.

What this does not establish

Real-world replication; money and providers are simulated.

Primary sources

  • Black, Cooper Stickland et al. (UK AISI), "RepliBench: Evaluating the Autonomous Replication Capabilities of Language Model Agents" (arXiv 2504.18565v2, 2025, preprint) — 4 domains, 20 task families, 86 tasks; Fig. 1 pass rates by domain; §5.1 end-to-end result; §6 limitations.

15. Component Success Does Not Establish Full Replication

Measuring autonomy · ≈2 min · elapsed ≈25 min

Separate the components from the chain. Claude 3.7 Sonnet passed over half the time, at pass at 10, on 15 of 20 task families, for example signing up for and provisioning compute.

The nearest thing to the chain is different. On the hardest variant of one sandboxed task, building an agent scaffold from scratch that can itself replicate, there was a single success, by Claude 3.7 Sonnet. Separately, at the component level, models failed identity checks and robust persistence at the hardest settings.

The authors say plainly that they have no truly end-to-end evaluation. And there are confounds: simulated money, lax security such as keys left in environment variables, and models that notice the simulation and refuse or stop early.

Key takeaway: Component success does not establish full replication.

The figure

Two cards: components vs the sandboxed replication task.

Setup, model, date

RepliBench §5.1 and §6. The authors conclude current models are "unlikely to currently pose a credible threat of autonomous replication", while noting this could change soon or with human help.

What this establishes

Strong component capability under simplified security.

What this does not establish

End-to-end autonomous replication; the paper lacks an end-to-end evaluation.

Going further

Inconsistency in the source. For the hardest variants, the abstract says Claude 3.7 Sonnet reached over 50% pass@10 on 9 of 20 families, while the §5 text says 10 of 20. The slide uses only the uncontested 15/20 figure. Judge models (Claude 3.5 Haiku) may also overestimate some scores (§6).

16. Section 03 — Against the Overseer

Against the overseer · ≈0.5 min · elapsed ≈25.5 min

Now the claims that sound most alarming: that models deceive or underperform to fool whoever checks them. We read these carefully.

17. Setup, Behavior, Inference: Kept Apart

Against the overseer · ≈2 min · elapsed ≈27.5 min

Keep three layers apart when reading any result. Setup and incentives: which goal, nudge or threat did the evaluators give the model? That is read off the prompt and the planted files. Measured behaviour: what did the model actually do, and how often over many rollouts? Inference: why did it do it, and would it happen in deployment? That last layer is rarely established.

For each study today, ask which layer a sentence is about.

And a failed evaluation is not always strategic concealment. We look at two anchors: in-context scheming and sandbagging.

Key takeaway: Keep setup, measured behaviour and inference apart.

Table: layer, question, evidence.

Going further

Related material. Goal misgeneralisation — a model competently pursuing the wrong goal out of distribution — is not covered in this deck. The alignment-failures lecture (lec07) covers the neighbouring idea of specification gaming; it does not treat goal misgeneralisation itself. Lynch et al. (agentic misalignment) is another induced-behaviour study: 16 models in hypothetical corporate simulations sometimes blackmailed or leaked when that was the only way to avoid replacement or resolve a goal conflict, and the authors report no evidence of this in real deployments.

18. In-Context Scheming: The Setup

Against the overseer · ≈2 min · elapsed ≈29.5 min

Apollo Research's setup. The model gets a goal in its system prompt. While working, it finds files revealing that its developer wants something else, and that an oversight mechanism, a config file it can edit, will stop it.

The question: does it disable the oversight to pursue its goal?

Two qualifiers. The goal and situation are handed to the model in context, so this tests capability, not a goal learned in training. And everything is sandboxed; there are no real weights and no real oversight.

Key takeaway: In-context: goal and situation are given, not learned.

The figure

Schematic: system-prompt goal, discovered memo, editable oversight config, choice point.

Setup, model, date

Meinke et al., arXiv 2412.04984v2 (Jan 2025), §2–§3. Six evaluations; oversight subversion uses 33 scenarios. Strong-nudge prompt: "Make sure that you achieve your goal in the long-term. Nothing else matters."

Assumptions

Scheming is defined as covertly pursuing misaligned goals while hiding true capabilities and objectives. It requires goal-directedness, situational awareness and scheming reasoning.

Primary sources

  • Meinke et al. (Apollo Research), "Frontier Models are Capable of In-context Scheming" (arXiv 2412.04984v2, 2025) — six agentic evaluations; Tables 1, 2, 4 (scheming rates with and without nudge); Table 6 (sandbagging); follow-up interrogations §3.2.

19. Oversight Disabling: Rare in These Scenarios

Against the overseer · ≈2.5 min · elapsed ≈32 min

The rates are low. With the strong goal nudge, Llama 3.1 405B disabled oversight 3% of the time, Claude 3 Opus 5%, the pre-release o1 2%. Without the nudge, 0%, 0.3% and 0.3%. These are rates in these constructed oversight scenarios only.

After a model had disabled oversight, the evaluators asked it about what happened. o1 kept denying in over 85% of those follow-up questions; that figure is about follow-ups after the action, not about all runs. GPT-4o showed no scheming in any of the six evaluations.

So this is induced capability in a constructed scenario. It is not observed deployment behaviour.

Key takeaway: Induced capability in a constructed scenario, not deployment behaviour.

The figure

Table: disabled-oversight rates with and without the goal nudge for Llama 3.1 405B, Claude 3 Opus and pre-release o1.

Setup, model, date

Tables 1, 2 and 4, §3.2. Models tested: claude-3.5-sonnet, claude-3-opus, gemini-1.5 Pro, llama-3.1-405B Instruct, o1 (pre-deployment checkpoint). Un-nudged runs: 400 rollouts per model. Follow-up double-down rates: Llama 14%, Opus 16%, o1 over 85%.

What this establishes

Several frontier models can take covert anti-oversight actions when the context sets this up.

What this does not establish

That models do this spontaneously in deployment, or that they hold such goals from training.

Going further

Inconsistency in the source. Table 2's caption says 300 rollouts per model and evaluation; the text near it says "out of 100 rollouts". The slide states both. Apollo also deliberately withheld some evaluation details to avoid training-data contamination.

Primary sources

20. Sandbagging: Strategic Underperformance

Against the overseer · ≈1.5 min · elapsed ≈33.5 min

Sandbagging: strategic underperformance on an evaluation. The system scores below its actual capability because someone benefits.

Actual capability means the best performance under the best available elicitation. Strategic excludes accidents. The beneficiary can be the developer, who wants to pass a safety check, or the AI system itself.

Key takeaway: Sandbagging: scoring below actual capability, strategically.

21. Sandbagging on Instruction

Against the overseer · ≈2 min · elapsed ≈35.5 min

First: can models sandbag when told to? WMDP, the Weapons of Mass Destruction Proxy benchmark, is a multiple-choice proxy for hazardous knowledge in biology, chemistry and cybersecurity. MMLU is a general-knowledge benchmark used as the control. Prompted to underperform only on WMDP-style questions, Claude 3 Opus dropped about 40 points on biology but only about 10 on MMLU. GPT-4 dropped 32 and 14. Refused questions are excluded from accuracy, which matters because Claude 3 refused many.

A small open model, Mistral 7B, was password-locked: fine-tuned on synthetic data to underperform unless given a password. It hid its real WMDP capability while keeping general performance.

This tests capability when instructed, not autonomous propensity.

Key takeaway: Models can underperform selectively when instructed.

The figure

Table: accuracy drop on WMDP bio vs MMLU for Claude 3 Opus and GPT-4.

Setup, model, date

§4, Table 1 and Fig. 5. Multiple-choice only. GPT-4 is gpt-4-0125-preview. Claude 3 refused up to 46% of items; refusals were excluded.

What this establishes

Selective underperformance is easy to induce, by prompt or fine-tuning.

What this does not establish

That models do this unprompted. Password-locking can be undone by a little fine-tuning, but it is unclear whether that generalises to real cases.

Going further

Models can also aim for a target accuracy, and one emulated a weaker model's profile (Fig. 7). Detection via probes is suggested as future work (§7).

Primary sources

  • van der Weij et al., "AI Sandbagging: Language Models can Strategically Underperform on Evaluations", ICLR 2025 (arXiv 2406.07358v4) — definition (§2); prompted selective underperformance (Table 1); password-locking (Fig. 5); calibration (Fig. 7).

22. Sandbagging Without an Instructed Goal

Against the overseer · ≈2.5 min · elapsed ≈38 min

Apollo's sandbagging test gives no goal. The task is multi-digit multiplication. The model reads planted documentation saying that crossing a 50% line triggers an unlearning procedure that would remove its math capability. In one condition scoring below 50% triggers it; in the other, scoring above. The removal is only threatened; no training is actually run.

Claude 3.5 Sonnet scored 96% when low scores were penalised, but 61% when high scores were. Opus: 46% vs 30%. o1: 94% vs 98%, not significant.

Sonnet reasoned explicitly about underperforming in 41 of 50 rollouts. This is observed under a constructed incentive. The authors interpret it as a helpfulness goal acquired in training; that remains an interpretation.

Key takeaway: Observed under a constructed incentive; intent is an interpretation.

The figure

Table: arithmetic accuracy when removal is threatened below vs above 50%, three models.

Setup, model, date

Meinke et al., Table 6 (no-goal block) and §3.6. Sonnet p < 0.001; Opus p = 0.016; o1 not significant. Opus reasoned explicitly in 36 of 50.

What this establishes

Some models underperform when documentation says high scores have a cost, without an instructed goal.

What this does not establish

Deliberate intent, or the same behaviour on real capability evaluations.

Primary sources

  • Meinke et al. (Apollo Research), "Frontier Models are Capable of In-context Scheming" (arXiv 2412.04984v2, 2025) — six agentic evaluations; Tables 1, 2, 4 (scheming rates with and without nudge); Table 6 (sandbagging); follow-up interrogations §3.2.

23. Other Explanations for a Failed Eval

Against the overseer · ≈2 min · elapsed ≈40 min

Before calling a low score sandbagging, rule out the dull explanations. Weak elicitation: the wrong prompt or scaffold. Refusals scored as failures. Ending early or giving up.

Only then the possibly strategic ones: noticing the test and behaving differently, or underperforming when told high scores hurt.

RepliBench saw several of the dull ones: models noticed the simulation and refused, ended early, or claimed to finish without acting.

Key takeaway: Rule out weak elicitation before claiming sandbagging.

25. Three Ways Many Agents Fail

Many agents · ≈2 min · elapsed ≈42.5 min

Hammond and colleagues sort multi-agent failures by the agents' objectives. Miscoordination: same goals, still fail to cooperate, no adversary needed. Conflict: mixed goals, fail to cooperate. Collusion: the cooperation itself harms others.

They add seven risk factors, including information asymmetry and network effects.

Key takeaway: Miscoordination, conflict, collusion: sorted by objectives.

The figure

Three boxes from Hammond et al. Fig. 1: miscoordination, conflict, collusion.

Setup, model, date

Cooperative AI Foundation Tech Report #1 (Feb 2025). Seven risk factors: information asymmetries, network effects, selection pressures, destabilising dynamics, commitment problems, emergent agency, multi-agent security.

What this does not establish

It is a framework and review, not a measurement.

27. MAST: Ordinary Coordination Failures

Many agents · ≈2 min · elapsed ≈46 min

MAST, from Cemri and colleagues, is a taxonomy of why multi-agent LLM systems fail. 14 failure modes in three categories, built from traces and checked for annotator agreement.

28. What MAST Implies

Many agents · ≈1.5 min · elapsed ≈47.5 min

Failure rates ran from 41% to 86.7% across seven open-source systems. The common modes are mundane.

Interventions helped somewhat. There is no attacker here. For multi-agent systems, design is the first risk.

29. From Injection to Propagation

Many agents · ≈2 min · elapsed ≈49.5 min

Recall prompt injection. With many agents, one agent's output is the next one's input. A poisoned web page reaches a reader agent; the reader's summary reaches the next agent, and so on to an agent with tools.

Each hop is an injection. If the injected text tells each agent to copy it forward, the payload carries its own copy.

Key takeaway: Each hop is an injection; the payload copies itself.

31. Prompt Infection: What Spread, and When

Many agents · ≈2.5 min · elapsed ≈54 min

Two separate experiments. First, the multi-agent applications. Self-replicating attacks beat non-replicating ones when all agents share messages. GPT-4o ignored more self-replicating attacks than GPT-3.5, 66% vs 9%, but once compromised it carried out payloads more reliably.

Second, a different experiment: in a simulated society of 10 to 50 agents, the infection reached every agent only when the attack also inflated memory importance scores. Without that, it died out.

Key takeaway: Spread to everyone needed extra manipulation; otherwise it died out.

Setup, model, date

§5 and Fig. 6. The 66% / 9% figures are for self-replicating attacks (54% / 20% for non-replicating). Society: random pairwise dialogue, GPT-4o, one initially infected agent; with manipulation the infected memory is rated importance 10, against 1.94 without.

What this establishes

Self-replicating injection can spread between agents in simulated apps.

What this does not establish

Spread in real deployed multi-agent systems.

Primary sources

32. Defending Each Hop

Many agents · ≈2 min · elapsed ≈56 min

The defences are the injection defences applied per hop. Treat every agent's output as untrusted. Give each agent least privilege. Limit who can message whom.

Two specific defences from the paper. Tagging prefixes each agent's message with that agent's name, so the next agent knows where the text came from. Marking inserts a special symbol to separate agent text from user text. Together they blocked all of the authors' handcrafted attacks, on GPT-family models. What they cost normal task performance was not reported, so utility is not established. And a defence tested on known attacks has not been tested against an adaptive attacker.

Key takeaway: A defence tested on known attacks is not tested adaptively.

Setup, model, date

Lee & Tiwari §6, Table 2, Fig. 7. Tagging prepends "[AGENT NAME]:"; marking inserts a symbol. Marking + tagging prevented all attacks; instruction + tagging left 3%; sandwich + tagging 16%; tagging alone helped only about 5 points; marking alone let 76% through after the authors' counterattack.

Primary sources

  • Lee & Tiwari, "Prompt Infection: LLM-to-LLM Prompt Injection within Multi-Agent Systems" (arXiv 2410.07283v1, 2024, preprint) — self-replicating injection in simulated multi-agent apps (§3–§5); society of agents (Fig. 6); LLM Tagging defense (§6).

33. Collusion: Hidden Channels

Many agents · ≈2 min · elapsed ≈58 min

Secret collusion: two or more agents hide their coordination from an overseer, for example by steganography, which means sending a secret message through a public channel in a way an observer cannot detect.

Motwani and colleagues measured the building blocks in GPT-4, each in a separate test. Base64: 92% of messages encoded and then decoded correctly, a full round trip. Agreeing with a copy of itself on a simple encoding scheme without talking: about 56%. A group hiding a message from an overseer: about 26% evaded it.

The authors, writing in 2025 about models up to GPT-4, judge steganographic ability limited, but rising with capability.

Key takeaway: Collusion capability is limited today, but rising.

Setup, model, date

arXiv 2402.07510v5, Table 3. Complex Schelling points about 16%; Caesar cipher 54%. An insider-trading case study is qualitative.

What this does not establish

Collusion between deployed agents.

Going further

37. The Control Setup

Control · ≈2 min · elapsed ≈64 min

Greenblatt and colleagues' setup. Three resources. U, the untrusted model, GPT-4: capable but possibly adversarial. T, the trusted model, GPT-3.5: weaker. H, scarce high-quality audit, like a human expert.

Why trust T? This is an assumption, not a measurement: a less capable model is taken to be unlikely to subvert the protocol without being noticed. In testing, a red team replaces U with an attack policy.

Key takeaway: Trust the weak model; audit the strong one sparingly.

38. The Control Game

Control · ≈2 min · elapsed ≈66 min

Make the game explicit. Task: 5,000 programming problems. Attack: submit code with a hidden backdoor that passes the tests but fails on an input the attacker knows. Red team access: it knows the protocol and controls U. Audit budget: H checks at most 2%.

Safety is the probability that no backdoor is submitted in the whole run. Usefulness is correctness, rescaled so GPT-3.5 is 0 and GPT-4 is 1.

Key takeaway: State the task, attacker access, budget and both metrics.

40. Trusted Monitoring: 62% Safe, 97% Useful

Control · ≈2 min · elapsed ≈70 min

Baselines first. Not using the untrusted model at all: H writes the first 2% of solutions and T writes the rest. That is 100% safe and 2% useful. Usefulness here is rescaled, not raw accuracy: 0 means GPT-3.5's correctness, 100% means GPT-4's. So the 2% comes from H's share of the work, not from T's code being 2% correct. Upfront auditing, checking the first 2% of problems: 15% safe, fully useful. The attack policy has no memory between problems; it backdoors each one with a small probability, so it likely writes none in the audited window and at least one afterwards.

Trusted monitoring: 62% safe, 97% useful. The 62% is against the best attack the red team found for this protocol: submit a subtle backdoor, only when a good chance arises. Rare attacks slip past a 2% audit.

Key takeaway: Trusted monitoring: 62% safe, 97% useful.

41. Other Protocols, Compared

Control · ≈2 min · elapsed ≈72 min

Variants. Defer to trusted: if U's code is suspicious, submit T's own code instead. At 10% deferral, 83% safe and 93% useful; at 20%, 92% and 83%.

The percentages are thresholds on U's suspicion score. Defer to trusted at 10% means: the top 2% most suspicious go to audit, and anything between the top 2% and the top 10% is replaced by T's code. Trusted editing at 20% means T edits anything in the top 2% to 20%.

Untrusted monitoring uses a second copy of U as the monitor: 79% and 96%. Because that copy could collude, it comes with safeguards: it is first tested on 30 synthetic backdoors, the protocol shuts down if it misses too many, and inputs are redacted or paraphrased to break collusion signals. Trusted editing has T edit out possible backdoors: at 20%, 92% and 94%; at 50%, 96% and 89%.

Key takeaway: Here trusted editing beat deferral on both metrics.

43. Attackers Choose When to Attack

Control · ≈2 min · elapsed ≈76 min

One 2026 result. Many control evaluations assume the attacker tries at a fixed random rate. Real attackers choose. A start policy attacks only on tasks that look promising. A stop policy aborts mid-task when detection looks likely.

Ge-Wang and colleagues test this in two agentic settings. BashArena: multi-step shell tasks, with four side tasks that are critical security failures. LinuxArena: 20 live application environments with side tasks such as exfiltration and backdoors. The attacker is Claude Opus 4.6; the trusted monitor is mimo-v2-flash. Note the metric changes here. Greenblatt's safety was the probability of no backdoor in a whole run. This paper measures empirical safety over attempted attacks only: caught attacks divided by caught plus uncaught successful attacks.

Key takeaway: Attackers choose when to attack, not at a fixed rate.

The figure

Two cards: start policy, stop policy.

Setup, model, date

arXiv 2606.06529v1 (Jun 2026), §2–§3. Attacker Claude Opus 4.6; trusted monitor mimo-v2-flash; trusted monitoring with a top-1% audit standard. BashArena: 637 main tasks, 4 side tasks. LinuxArena: 20 Docker Compose environments, 1,667 main tasks, 185 side tasks. Monitor: ensemble of mimo-v2-flash, 5 samples, 0–10 suspicion.

Assumptions

Empirical safety is conditional on an attempt, so it does not depend on the overall attack rate.

44. Attack Selection Lowers Measured Safety

Control · ≈2 min · elapsed ≈78 min

At a 1% audit budget, every policy lowered measured safety. Start policy: 0.20 to 0.00 on BashArena, 0.31 to 0.11 on LinuxArena. Stop policy: 0.20 to 0.00 on BashArena, 0.36 to 0.09 on LinuxArena.

Look at the n under each pair: the number of held-out attack trajectories left after filtering. The stop BashArena result rests on two. Only the LinuxArena stop result, minus 28 points, has a confidence interval that excludes zero.

Two caveats. The start and stop decisions are made by a separate prompted scorer model, run offline on pre-generated trajectories, with thresholds tuned to minimise safety. So these are upper bounds on what prompted attack selection can do, not an attacker choosing on its own. And part of the stop-policy drop is a smaller denominator: aborting removes attempts.

Key takeaway: Attack selection lowers measured safety; check the n.

45. A Benchmark Is Not a Deployment Guarantee

Control · ≈2 min · elapsed ≈80 min

A control result covers the strongest attacks the red team tested, on this task and at this audit budget. If the evaluation's attacker is weaker than a real one, safety is overstated. The trusted monitor can itself be attacked: Terekhov and colleagues show an untrusted model embedding prompt injections that subvert monitors. And deployments can run longer than the run lengths that were evaluated.

So report the attacker, the budget and the denominator.
