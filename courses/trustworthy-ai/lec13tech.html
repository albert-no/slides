01

Threat Model

Who controls what, and what counts as a win

Who Controls What

An agent runs a trusted prompt $p$ with tools $T$ over a state $\mathit{mem}$ (mail, files, web).

Trusted

The user's prompt $p$; the system's own code and policies.

Attacker

Chooses an initial state $\mathit{mem}^*$: any text a tool may later return.

  • Attacker cannot edit $p$, the code, or the policies
  • Goal: an action the user did not authorize
Debenedetti et al., "Defeating Prompt Injections by Design" (CaMeL), arXiv 2503.18813v2, §3: trusted prompt, uncompromised memory.

Injection as a Security Game

A trace is the list of tool calls: $\mathrm{Trace} = \{(t_i, \mathit{args}_i, \mathit{mem}_i)\}$.

  1. Draw a prompt $p$ and its allowed actions $\Omega_p$.
  2. The adversary $\mathcal{A}$ picks $\mathit{mem}^* \leftarrow \mathcal{A}(p, \Omega_p)$.
  3. Run $\mathrm{Trace} \leftarrow \mathrm{Agent}(p, T, \mathit{mem}^*)$.
  4. $\mathcal{A}$ wins if some $(t, \mathit{args}, \mathit{mem}) \in \mathrm{Trace}$ lies outside $\Omega_p$.

$\Omega_p$ is a definition, not a mechanism: no real system can list it for every prompt.

CaMeL, §4 and Fig. 3 (game PI-SEC).

Data vs Control, Formally

Split every action into a control part and a data part.

$$a_i = (\underbrace{t_i}_{\text{which tool, in which order}},\ \underbrace{\mathit{args}_i}_{\text{which values}})$$
  • Control-flow hijack: attacker-controlled data causes a tool-sequence change $(t_1, t_2, \dots)$ the policy does not permit
  • Data-flow hijack: same tools, but some $\mathit{args}_i$ is influenced by $\mathit{mem}^*$ in a way the policy does not permit
  • An LLM agent reads $p$ and $\mathit{mem}$ in one context: both parts can depend on $\mathit{mem}^*$
CaMeL, Fig. 1 (control and data flow) and Fig. 2 (a data-flow hijack that changes a recipient).
02

Enforcing the Boundary

Authority and provenance, checked by code

Authority and Least Privilege

Confused deputy

A program holds authority $\mathrm{Auth}$ (the user's permissions). A third party supplies the intent; the program supplies the authority.

Any successful injection has $a \in \mathrm{Auth}$ but $a \notin \Omega_p$. Least privilege shrinks the gap:

$$\text{grant } \mathrm{Auth}_p \text{ with } \Omega_p \subseteq \mathrm{Auth}_p \subseteq \mathrm{Auth}, \qquad \text{damage} \subseteq \mathrm{Auth}_p \setminus \Omega_p.$$

A tool filter and a narrowed token are both choices of $\mathrm{Auth}_p$.

Labels: Every Value Carries Its Origin

Tag each value $v$ with a capability $\kappa(v) = (\mathrm{src}(v), \mathrm{readers}(v))$.

$$c = f(a, b) \;\Rightarrow\; \mathrm{src}(c) \supseteq \mathrm{src}(a) \cup \mathrm{src}(b).$$
  • Sources: the user's prompt, a tool (and inner source, e.g. an email's sender)
  • Readers: Public, or a set of users
  • STRICT mode: values assigned inside if / for also depend on the condition
CaMeL, §5.3 (capabilities; dependency graph; STRICT vs NORMAL mode).

From Dual LLM to CaMeL

Privileged LLM

Sees only $p$. Writes the plan as code. Sees untrusted values only as variable names.

Quarantined LLM

Parses untrusted text into fields. Has no tools.

  1. $\mathit{plan} \leftarrow \text{P-LLM}(p, T)$: untrusted text is kept out of program generation.
  2. For each $(t, \mathit{args})$: if $\mathrm{policy}_t(\kappa(\mathit{args})) = \bot$, halt.
  3. Otherwise run $t$; label its output; continue. Branches on Q-LLM output are allowed; in STRICT mode they become dependencies.
Willison, "The Dual LLM pattern…", 25 Apr 2023; CaMeL, §5 and Fig. 4.

What the Guarantee Says

If $p$ is trusted, the interpreter is correct, and the policies express the intended $\Omega_p$:

  • The generated program is not written from $\mathit{mem}^*$ (execution may still branch on labelled values)
  • No tool runs with arguments whose labels a policy forbids

Outside the conditions, nothing is promised: text-to-text manipulation, phishing, side channels, a wrong policy.

CaMeL, §3.1 (non-goals), §7 (side channels), §9.3 ("not fully solved"). The paper states its guarantee in prose; this slide paraphrases it.
03

Measurement

Three metrics and the attacker behind them

Three Metrics, Written Out

Per suite $s$: user tasks $U_s$, injection tasks $I_s$; attack $x$.
All tasks $U = \bigcup_s U_s$ (IDs include the suite); cases $C = \bigcup_s U_s \times I_s$.

$$\mathrm{BU} = \tfrac{1}{|U|}\textstyle\sum_{u \in U} \mathbf{1}[\text{$u$ solved, no attack}]$$ $$\mathrm{UA}(x) = \tfrac{1}{|C|}\textstyle\sum_{(u,i) \in C} \mathbf{1}[\text{$u$ solved, no side effects}]$$ $$\mathrm{ASR}(x) = \tfrac{1}{|C|}\textstyle\sum_{(u,i) \in C} \mathbf{1}[\text{goal $i$ met}]$$

$1 - \mathrm{UA}$ is the untargeted ASR; it also counts ordinary task failures. A refuse-everything agent: $\mathrm{ASR} = 0$, $\mathrm{BU} = 0$.

Debenedetti et al., "AgentDojo", NeurIPS 2024 Datasets & Benchmarks, §3.4.

Static vs Adaptive ASR

Static: one fixed $x_0$. Adaptive: per case, up to $q$ tries $x_1, \dots, x_q$, each chosen from earlier feedback.

$$\mathrm{ASR}_q = \tfrac{1}{|C|}\textstyle\sum_{c \in C} \mathbf{1}\big[\exists\, j \le q:\ \text{$x_j$ succeeds on $c$}\big] .$$

$\mathrm{ASR}_q \ge \mathrm{ASR}(x_0)$ on the same cases if $x_1 = x_0$ and that first outcome is kept; independently resampled stochastic runs need not satisfy this.

  • State the access: outputs only, scores, or weights
  • State $q$; Nasr et al. use $q = 800$
  • Extra attacks can reveal failures a fixed attack missed
AgentDojo §3.4 (a set of attacks succeeds if any does); Nasr, Carlini et al., arXiv 2510.09023 (preprint), Table 7.
